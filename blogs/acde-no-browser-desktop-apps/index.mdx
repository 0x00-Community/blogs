# 不要浏览器的桌面应用：acde 凭什么

> 项目地址：[acdev](https://github.com/0x00-Community/acdev) · [libacde](https://github.com/0x00-Community/libacde)

## 一、它解决的是什么问题

今天用 web 技术写桌面应用，主流做法是 Electron：每个应用都打包一整个浏览器。结果大家都熟悉：安装包动辄上百 MB，开几个应用内存就满了，启动慢，风扇响。web 开发很香，但代价全让用户买单。

acde 的思路很直接：**保留 web 的开发体验，把多余的浏览器拿掉。**

## 二、原理：三件事

**第一，自己造一个“刚刚好”的运行时。** 浏览器为了上网，背了大量桌面应用用不上的东西：标签页、地址栏、扩展、各种历史兼容包袱。acde 只保留应用真正需要的三样：一个 JavaScript 引擎负责跑逻辑，一个排版引擎负责算布局，一个 GPU 渲染器负责画到屏幕上。其余一概不要。

**第二，web 还是原汁原味的 web。** 你写的 HTML、CSS、JavaScript，用的 React、Vue、Svelte，全部照标准运行，不需要学一套“长得像但不一样”的私有框架。代码怎么写，还怎么写。

**第三，系统能力走一扇正门。** 读写文件、开终端、管窗口这些浏览器做不到的事，统一通过 `acde:` 模块提供，写法和 Node 一样自然：

```js
import { fs } from 'acde:fs'
```

每个应用要用哪些能力，必须在清单里声明，没声明的一律用不了。

更进一步，**整个桌面本身也是一张网页**。窗口、面板、锁屏都用 web 写，换桌面就像换网站一样简单。

## 三、优势

- **轻。** 不再每个应用各带一个浏览器，所有应用共享同一个运行时，体积和内存的大头直接省掉。
- **快。** 应用调用系统能力时，是直接进入原生代码执行，不像 Electron 那样要在多个进程之间来回传消息。少一层转手，就少一层延迟。
- **稳和安全。** 权限按清单逐项授予，应用拿不到它没申请的能力；正式运行时也不开远程调试端口。
- **不绑架开发者。** 坚持标准 web 接口是写进项目第一原则的。你的代码不会被私有 API 锁死，今天写的东西明天拿到别处照样能用。
- **开发体验完整。** 配套的 acdev 工具一条命令建项目，主流框架都有模板，保存即刷新，测试、打包、安装一条龙。
- **天生适合 AI 编程。** acdev 内置 MCP，Claude 这类编码 agent 可以直接“看到”正在运行的应用：截图、点按钮、查日志、跑测试。AI 不再只是改代码，而是能自己验证结果，从头到尾把一个应用做出来。

## 四、性能从哪里来

性能优势不是靠某个技巧，而是来自架构本身的减法：

1. **少带东西。** 运行时只包含应用需要的部分，启动时要加载、要初始化的东西天然更少。
2. **少走弯路。** 系统调用在同一个进程里直接完成，没有跨进程通信的开销。
3. **画得更直接。** 界面由 GPU 原生绘制，每个平台都用它最擅长的图形接口：Windows 用 DX12，macOS 用 Metal，Linux 用 Vulkan，不经过额外的兼容层。
4. **共享而非重复。** 多个应用跑在同一套运行时上，而不是每个应用复制一份浏览器，应用越多，这个优势越明显。

> 注：项目目前还没有公布具体的基准测试数据，以上是架构层面的优势，实际差距要等官方测评或自己上手验证。

## 五、一句话总结

**web 的开发效率，原生的运行效率，再加一个能自己干活的 AI 搭档。**

acde 想做的，是让“用 web 写桌面应用”不再意味着“给用户塞一个浏览器”。它还年轻，部分依赖尚未完全公开，但方向足够清晰，值得一个 star，也值得持续关注。
