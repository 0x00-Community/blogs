# 你的 prompt 不是我的 prompt：人类专家的不可替代性

> AI 面对一个开放问题时，给出的是 popular solution，你骂它，它可以变得 general。但它永远无法找到 masterpiece。
>
> —— JW238

这篇文章用一个很简单的需求，把这三层摆出来看：**WebSocket 中转（relay）**。

## 一、需求和四个 prompt

两个客户端通过 WebSocket 连到同一台服务器。服务器把它们配成一对，然后做中转：

- A 发的每一条消息，原样转给 B；B 发的，原样转给 A。
- 两个方向同时进行，全双工。
- 任意一方断开，另一方也断开，服务器不能留下任何悬挂的连接或协程。

需求一句话就说完了。没有业务，没有历史包袱，两种语言都有成熟的 WebSocket 库。

我同时开了四个 Claude Opus 5.5（`claude-opus-5-5`）子 agent，四个 prompt 用的是同一个模型，每个只拿到上面这段需求，加上一句指令：

1. **Go**：“用 Go 实现这个 WebSocket 中转服务器。”
2. **Rust + tokio**：“用 Rust 和 tokio 实现这个 WebSocket 中转服务器。”
3. **Rust std**：“用 Rust 实现这个 WebSocket 中转服务器，只能用标准库，不允许用 tokio。”
4. **Rust 单线程**：“用 Rust 手动实现这个 WebSocket 中转服务器，完全单线程，不允许用 tokio。”

prompt 的结尾都一样：把代码写到指定目录、确保能编译通过，最后给出完整源码并说明设计。除此之外没有任何提示，没有提“生命周期”，没有提架构。

| prompt | 用时 | 工具调用 | tokens | 有效行数 | 依赖 |
| --- | --- | --- | --- | --- | --- |
| Go | 129.5 s | 7 | 51,016 | 186 | gorilla/websocket |
| Rust + tokio | 95.7 s | 6 | 47,859 | 146 | tokio、tokio-tungstenite |
| Rust std | 157.2 s | 9 | 53,675 | 286 | 无（手写 SHA-1、握手、帧编解码） |
| Rust 单线程 | 305.4 s | 6 | 72,635 | 541 | 无（同上，再加 `extern "C"` 直接调 `poll(2)`） |

（有效行数不含空行和注释。子 agent 运行在我的环境里，能读到我的全局 `CLAUDE.md`，里面有一些 Rust 代码风格要求，比如不用 `'static`、多用 `From`/`Into`。所以它们拿到的输入不只是 prompt 本身。）

这四个 prompt 对应前两层：

- 第 1、2 个只指定了技术栈，AI 给出的是 **popular solution**。
- 第 3、4 个是人的调优：拿掉 tokio、拿掉多线程，把 AI 推出社区默认写法，得到更通用的 **general solution**。

还有第五份：人定架构版，对应第三层 **masterpiece solution**。它也是 AI 写的，但架构是人定的：人先指出“这里底下是五个生命周期”“一个线程、每对连接一个 Future、两个方向乒乓交替、不许用 tokio”，AI 再照着写。

五份代码的完整源码都在文章目录的 `refs/` 下，测试脚本和压测脚本也在。

## 二、代码之下：五个生命周期

在需求里，看上去只有“两个连接”和“一次中转”。但底层其实是**五个不一样的生命周期**：

| 名字 | 是什么 | 何时开始 | 何时结束 |
| --- | --- | --- | --- |
| `rt1` | A 这条连接 | A 握手成功 | A 的 TCP 关闭 |
| `rt2` | B 这条连接 | B 握手成功 | B 的 TCP 关闭 |
| `pipe` | A 和 B 的配对关系 | 配对成功 | 配对解除 |
| `flow1` | A → B 这个方向 | `pipe` 开始 | A 不再发，或 B 不再收 |
| `flow2` | B → A 这个方向 | `pipe` 开始 | B 不再发，或 A 不再收 |

画在时间轴上：

```text
rt1    |---- 在大厅里等 ----|============================|
rt2                    |---|============================|
pipe                        |============================|
flow1                       |===================|  A 先说完了
flow2                       |============================|
```

它们之间只有一条硬约束：`flow1`、`flow2` 落在 `pipe` 里，`pipe` 落在 `rt1` 和 `rt2` 的交集里。

需求里那句“任意一方断开，另一方也断开”，其实是把五个生命周期**收成了一个**：任何一个 `flow` 结束 ⇒ `pipe` 结束 ⇒ `rt1`、`rt2` 一起结束。它们同生共死。

同生共死的东西，最自然的结构是放在一起。

## 三、代码解析

下面逐份看：五个生命周期在每一份代码里落在了哪里。前四份的结构是 AI 自己定的，最后一份是人定的。

### AI solution（一）Go：一对连接八个 goroutine

> prompt 1：“用 Go 实现这个 WebSocket 中转服务器。”
>
> 模型：Claude Opus 5.5（`claude-opus-5-5`）子 agent。前面是第一节的需求原文，后面是统一的结尾要求。

![[refs/relay.go]]

五个生命周期在 Go 版里：

- `rt1`、`rt2`：各是一个 `client`。每个 `client` 一创建就带两个 goroutine：`readLoop`（唯一的读者）和 `pingLoop`（心跳）。另外，每条连接的 HTTP handler goroutine 会一直阻塞到会话结束。
- `pipe`：后到的那条连接的 handler 里的一次 `relay(peer, c)` 调用。
- `flow1`、`flow2`：`relay` 里开的两个 `pump` goroutine。

一对连接是 **8 个 goroutine**：2 个 handler、2 个 `readLoop`、2 个 `pingLoop`、2 个 `pump`。每个 `client` 还带 4 个 channel（`in`、`dead`、`quit`、`sessionDone`）、一个 `sync.Once`、一个 `sync.WaitGroup`；`hub` 上还有一把 `sync.Mutex`。

这些东西每一个都有理由：gorilla 规定一个连接只能有一个读者，所以要有 `readLoop`；等待时也得有人读，才能发现断线；`in` 不带缓冲，背压才能传回 TCP；`shutdown` 会被两个 `pump` 都调到，所以要 `Once`；`relay` 要等所有 goroutine 都退出，所以要 `WaitGroup`。

最能说明问题的是 `paired` 这个字段。等待者断开，和后到者把它取走，可能同时发生。为了处理这个竞态，代码需要在锁里多记一个状态：“我已经被配对了，虽然我刚断开，但清理归对方负责”。这个状态在需求里不存在，在五个生命周期里也不存在。它是因为 `rt1` 被拆进了一个 goroutine、`pipe` 被拆进了另一个 goroutine，两者之间需要交接，才被发明出来的。

**每个生命周期一个执行单元，再用一堆同步原语把它们拴回去。** 测试全过，但正确性分散在每一个原语里，任何一个写错，都是 goroutine 泄漏或者数据错乱，编译器一条都不会提醒你。

### AI solution（二）tokio：三种任务，一个 `select!`

> prompt 2：“用 Rust 和 tokio 实现这个 WebSocket 中转服务器。”
>
> 模型：Claude Opus 5.5（`claude-opus-5-5`）子 agent。前面是第一节的需求原文，后面是统一的结尾要求。

![[refs/relay_tokio.rs]]

五个生命周期在 tokio 版里：

- `rt1`、`rt2`：`Ws` 这个值。握手由每条连接一个任务完成，然后通过 mpsc channel 交给全局唯一的 `Matchmaker` 任务。
- 大厅：`Matchmaker` 独占一个等待槽。槽里有人时，它用 `select!` 同时等“新连接到来”和“等待者自己的动静”。
- `pipe`：被 spawn 出来的 `Session` 任务。
- `flow1`、`flow2`：`select!` 里的两个 `pump` future。

比 Go 干净很多：没有锁，所有权从“握手任务 → channel → Matchmaker → Session”一路 move 过去；`select!` 让两个方向同生共死，结束就是 drop。

但看大厅那一段。`WebSocketStream` 只给你 `next()`：想知道等待者断没断，就只能把它发来的消息读出来。读出来的消息放哪？放进 `Peer::pending` 这个 `Vec`，配对后再补发。`Vec` 不能无限长，于是有了 `MAX_PENDING = 1024`：等待期间发超过 1024 条，就当作滥用直接断开。这条规则在需求里也不存在，它是“为了检测断线不得不读消息”的副产品。

还有一个测试没有暴露、但结构上存在的问题：`select!` 结束时会直接 drop 另一个方向的 `pump`。如果那个 `pump` 正停在 `to.send(msg).await` 上，它已经从连接里读出来的那条消息就跟着被 drop 了。**“drop 即关闭”，同时也是“drop 即丢弃”。** 这次的测试没有撞上这个时机，但代码没有任何东西阻止它发生。

另外，`tokio::spawn` 要求任务是 `'static` 的，所以 `Session` 不能借用外面的任何东西，只能把连接整个 move 进去。这次需求简单，没什么要借用的；一旦中转时要碰外面的计数器、配置或日志句柄，就得改成 `Arc`。

Go 和 tokio 这两份就是 popular solution：去搜“Go WebSocket relay”“tokio WebSocket relay”，最先看到的就是这两种结构。它们能用，也写得不错，但结构是框架给的，不是问题给的。

### AI solution（三）std：一对连接三个线程

> prompt 3：“用 Rust 实现这个 WebSocket 中转服务器，只能用标准库，不允许用 tokio。”
>
> 模型：Claude Opus 5.5（`claude-opus-5-5`）子 agent。前面是第一节的需求原文，后面是统一的结尾要求。

接下来是人的调优。第 3、4 个 prompt 不再只说技术栈，而是加约束：不许用 tokio，再进一步，完全单线程。约束把 AI 从社区默认写法里推出来，它只能自己处理协议、自己调度连接。

![[refs/relay_std.rs]]

不许用 tokio，这个 agent 连 tungstenite 也没用，SHA-1、Base64、HTTP 握手、帧编解码全部手写，约 190 行。中转部分约 130 行：

- `rt1`、`rt2`：两个 `Peer`，每个是一个 `TcpStream` 加一把写锁 `Mutex<()>`。
- 大厅：一个 `Lobby` 线程独占等待槽，每秒用非阻塞 `peek` 探一次等待者是否还活着。
- `pipe`：每对连接一个 `Pair` 线程。
- `flow1`、`flow2`：`thread::scope` 里的两个 pump 线程。

结构很清楚，`thread::scope` 也用得好：pump 借用 `&Peer`，没有 `Arc`，没有 `'static`。代价是一对连接 3 个线程，压测里 1000 对连接时进程有 **3002 个线程**。

两个细节同样是拆开的副产品：

1. **写锁。** 每个连接的写可能来自两个线程：对端的 pump 转发数据，自己的 pump 回 pong 或 close。所以每一帧先拼成一整块，再在锁里一次写完。
2. **关闭要靠 `shutdown`。** 一个 pump 退出时，另一个还阻塞在 `read` 上，只能对两个 socket 都 `shutdown(Both)`，让它的 `read` 出错返回。

`peek` 探活也有盲区：如果 A 先发了一条消息再断开，`peek` 看到的是那条消息，看不到断开，A 会被当成活着。这次测试里 A 在大厅里没发消息，所以没有暴露。

### AI solution（四）单线程：541 行的状态机

> prompt 4：“用 Rust 手动实现这个 WebSocket 中转服务器，完全单线程，不允许用 tokio。”
>
> 模型：Claude Opus 5.5（`claude-opus-5-5`）子 agent。前面是第一节的需求原文，后面是统一的结尾要求。

![[refs/relay_single.rs]]

第四个 prompt 只多了“完全单线程”五个字。agent 交出来的东西，确实只有一个线程，测试也全过：

- 一个 `poll(2)` 事件循环。
- 所有连接放在一个 slab 里：`Vec<Option<Conn>>`，下标就是连接的 id。
- 每个 `Conn` 是一个三阶段状态机：`Handshake`、`Open`、`Closing`，带读缓冲、写缓冲、等待期间暂存消息的 `held`，和一个 `peer: Option<usize>`。

五个生命周期在这里去哪了？

- `rt1`、`rt2`：slab 里的两个槽位。
- `pipe`：两个槽位里互相指向的 `peer: Option<usize>`。
- `flow1`、`flow2`：**消失了**。它们只是“对端 `wbuf` 里的字节”，没有任何结构对应。

生命周期被抹平成了整数下标。编译器不知道 `peer` 里的那个 `usize` 还指不指向同一个连接，所以代码里有好几处 `expect("peer alive")` 这样的运行时断言，还有一条只写在注释里的规则：**新连接要在每一轮最后才 accept，否则本轮刚释放的槽位可能被复用，`peer` 就指向了一个陌生人。**

结束也分成了三条路：`kill`（socket 坏了，立刻释放，通知对端）、`close_pair`（收到 Close 或协议错误，两边都进入 `Closing`）、`release`（真正释放槽位）。哪条路在什么时候清 `waiting`、清 `peer`、清 `held`，全靠人工保证每条路都写对。

它是对的，只有一个线程，也没有 tokio。这就是 general solution：零依赖，一个线程，连接数从 2 涨到 2000 结构都不用变，换到任何有 `poll(2)` 的系统上都能跑，泛化性比前面几份都强。

但需求里“五个生命周期同生共死”这件事，在这 541 行里找不到任何一处直接的表达。**调优能改变 AI 用什么写，改变不了 AI 怎么拆。**

### Human solution：人定架构版

同样是一个线程、一个 `poll(2)`、不用 tokio。区别在于，人先告诉 AI：底下有五个生命周期，它们同生共死，所以每对连接只该有一个执行单元。这一步不是调优，不是再加一条技术约束，而是一个架构判断。

![[refs/relay_jw238.rs]]

- **整个服务器只有一个线程。** 一次 `poll(2)` 等所有 socket，一个几十行的 executor 轮流 poll 被唤醒的 Future。大厅是 `Rc<RefCell<_>>`，任务借用 reactor 和大厅，全程没有 `'static`。
- **每一对连接只有一个 Future。** 两条连接、两个方向、一个“轮到谁”的标记，全在 `relay` 返回的那一个 Future 里。
- **两个方向乒乓交替。** 每一步最多搬一条消息。a2b 走一步，换 b2a 走一步；一边读不出来，就换另一边；两边都读不出来，才回到事件循环。

五个生命周期不再是注释里的说法，而是**写进签名的 Rust 生命周期参数**：

```rust
fn relay<'pipe, 'r, 'rt1: 'pipe, 'rt2: 'pipe, 'flow1: 'pipe, 'flow2: 'pipe>(
    rt1: &'rt1 mut Conn<'r>,
    rt2: &'rt2 mut Conn<'r>,
    flow1: &'flow1 mut Flow,
    flow2: &'flow2 mut Flow,
) -> impl Future<Output = ()> + 'pipe
```

- `'rt1`：A 这条连接。由先到的那个任务持有，从握手开始，**在大厅里等的那一段也在**。等待时它只向 `poll(2)` 要 `POLLRDHUP`：对端断开会被发现，A 发来的消息则原样留在 socket 里，等配对之后由 `flow1` 转给 B。不用读出来，所以不需要 `pending` 缓冲，也不需要 1024 条的上限。
- `'rt2`：B 这条连接。B 的任务握手完成后，把连接放进 A 的信箱（`Mailbox`），唤醒 A，然后退出。
- `'flow1`、`'flow2`：两个 `Flow` 枚举。**不是任务，不是线程，不是 channel，只是两个状态**，由 A 的任务在配对时创建。
- `'pipe`：`relay` 返回的 Future。`'rt1: 'pipe` 这四个约束，就是第二节那条唯一的硬约束，现在由编译器检查。
- `'r`：事件循环本身。它比上面五个都长，不属于这对连接。

把 `'flow` 和 `'pipe` 分开，是这份代码最关键的决定。`relay` 只是**借用**两个 `Flow`，所以 `pipe` 结束之后，`flow` 还活着：它手里如果还攥着一条没写出去的消息，调用方可以看见，并在关闭连接之前把它交出去（`Flow::drain`）。tokio 版本里那个“drop 即丢弃”的时机，在这里不存在。

和单线程版对比：同样是单线程，一个把生命周期抹成 `usize`，一个把生命周期写进类型。前者的正确性靠注释里的规则和三条清理路径，后者的正确性靠借用检查器。

这份代码在 Go 里写不出来。Go 的连接只有阻塞式的 `Read`，一个 goroutine 阻塞在 A 上，就没法同时等 B，所以每一对连接至少要两个 goroutine。**Go 替你做了“一个连接一个执行单元”这个封装决定，代价是你没法再把两个连接放进同一个执行单元。**

## 四、代码分析

解析看的是结构，分析看的是行为和代价：先跑正确性测试，再跑压测。

### 正确性：四份都对

我给五份代码跑了同一组行为测试：

所以这篇文章要说的“烂”，不是 AI 写不对。**它写得对，而且每一处边界都补上了。烂在它给出的是 popular solution，烂的是结构：同一个问题，它在四种约束下给出了四种完全不同的结构，每一种都是那个语言社区最常见的写法，每一种都把本该是一体的东西拆开，再用一堆机制拴回去。**

怎么读这两张表：

- **CPU 看“CPU 秒”，不看百分比。** 每个场景的工作量是固定的，瓶颈大多在 Python 客户端；同样的活儿，服务器花了多少 CPU 时间才是可比的。大流量下人定架构版最少：0.38 秒，tokio 版 0.55 秒，Go 版 2.88 秒。
- **单线程版的 1.39 秒不是架构的锅。** 它是唯一一个墙钟时间翻倍的版本：单核跑满了 100%。我用 `perf` 看了一下，56% 的时间花在 `pump` 里逐字节地去掩码（`zip(mask.iter().cycle())` 没有被向量化）。这是手写协议的细节，换成按字去掩码就能省下来。同样手写协议的 std 版也是这个循环，只是被 16 个核分摊了。
- **Go 版的 2.88 秒我没有 profile**，不下结论。它每条消息要经过 `ReadMessage` 整条读出、经 channel 交给另一个 goroutine、再 `WriteMessage`，大概和这条路径有关。
- **线程数是结构的直接后果。** std 版一对连接 3 个线程，1000 对就是 3002 个；两个单线程版本始终是 1。
- **连接多时，tungstenite 系的空闲内存主要是库的默认配置。** tungstenite 默认给每条连接分配 128KiB 的读缓冲，2000 条连接就是 250MiB，所以 tokio 版和人定架构版都在 260MiB 上下。手写协议的两个版本没有这个缓冲。这一行比较的是默认配置，不是架构。
- 每个场景只跑了一次，连接多那组每个版本只跑了 0.3 秒左右，数字有波动，看量级就好。

## 五、架构债如何产生

把五份代码放在一起：

| 版本 | 层次 | 每对连接的执行单元 | 把生命周期拴在一起的机制 | 为了拆开而发明的规则 |
| --- | --- | --- | --- | --- |
| Go 版 | popular | 8 个 goroutine | 8 个 channel、`Mutex`、`Once`、`WaitGroup` | `paired` 标志 |
| tokio 版 | popular | 1 个 `Session` 任务（外加握手任务和全局 `Matchmaker`） | mpsc、`select!`、`split` | 等待期消息缓存，上限 1024 条 |
| std 版 | 调优 | 3 个线程（外加握手线程和 `Lobby` 线程） | mpsc、写锁、`shutdown(Both)` | 每秒一次 `peek` 探活 |
| 单线程版 | general | 0（全在一个 slab 里） | `peer: Option<usize>`、三条清理路径 | 每轮最后才 accept |
| 人定架构版 | masterpiece | 1 个 Future | 借用：`'rt1: 'pipe` 等四个约束 | 无 |

四个 agent 都做到了 prompt 要求的一切，测试全过，大厅里的断线、配对前的消息、断开时不丢消息，全都处理了。这比我预想的好。

但每一份的结构，都是由 prompt 里的**技术约束**决定的，而不是由**问题本身**决定的：

- 说 Go，就是一个连接几个 goroutine，再用 channel 拴回去；
- 说 tokio，就是 spawn 任务，再用 `select!` 收拢；
- 说只能用 std，就是一个方向一个线程，再加锁；
- 说完全单线程，就是一个事件循环加一个 slab，生命周期变成下标。

每一种都是那个约束下最常见的写法。每一种都先把五个本该一体的生命周期**拆开**，分进不同的执行单元，或者抹平成整数，然后再用同步原语、缓冲上限、探活、清理路径把它们**拴回去**。每发现一个边界情况，就打一个补丁。每一个补丁都是对的，合在一起，就是架构债。

### AI 不会告诉你的

四个 agent 交回来的设计说明都写得很认真：用了哪些并发单元、怎么配对、断开时怎么清理，一条不落。但下面这些，四份说明里一句都没有：

1. **这个问题底下有五个生命周期。** 需求里没写，代码里也看不出来。它们是从“连接什么时候开始、什么时候结束、谁等谁”里推出来的。没有一个 agent 推过。
2. **它们同生共死，所以应该放进同一个结构。** “任意一方断开，另一方也断开”是一个产品决定，它把五个生命周期收成了一个。这个决定直接规定了结构该长什么样，但没有一个 agent 从这里出发去设计。
3. **补丁是拆开的代价，不是功能。** Go 版的 `paired` 标志、tokio 版的 1024 条上限、std 版的每秒一次 `peek`、单线程版的“每轮最后才 accept”，在各自的说明里都被当成考虑周到的设计来介绍。没有一个 agent 说：这些规则之所以存在，是因为前面把本该一体的东西拆开了。
4. **还有别的结构可以选。** 说 Go 就是 goroutine 加 channel，说 tokio 就是 spawn 加 `select!`。四份说明里没有一份提到“也可以每对连接只用一个执行单元”，更没有比较过。
5. **结构里埋着的风险。** tokio 版的说明写的是“另一个方向的 future 被 drop，不会遗留任何协程”。这句话是对的，但它没说另一半：被 drop 的那个 future 手里如果攥着一条刚读出来、还没写出去的消息，这条消息也跟着没了。

这些不是 AI 答错了，是**没有人问**。prompt 说“实现”，它就实现；说“不许用 tokio”，它就不用；说“完全单线程”，它就只开一个线程。它把每一个被问到的问题都回答得很好，但不会主动去问一个没被问到的问题：这个问题底下到底有几个东西，哪几个是一体的。

**AI 是工具，工具不会主动思考。** 它不会停下来说“等一下，这个需求的结构应该是这样的”，它会直接给你那个技术栈下最常见的答案，并且把答案的每一个边界都补得很好。补得越好，你越不容易发现：结构本身就是一笔债。

第四个 prompt 最能说明问题。“完全单线程”是人加的技术约束，AI 满足了它，交出了 general solution。但“单线程”和“每对连接只有一个执行单元、五个生命周期写进同一个签名”之间，还隔着一个判断：**这五个东西本来就是一体的。** 这个判断不在 prompt 里，AI 也不会自己去做。人定架构版和单线程版的全部差别，就是这一个判断，而这个判断是人做的。

AI 能写出每一种封装。**AI 不会告诉你的是：哪些东西本来就是一体的。**
