# 测试先行：agent 时代，怎样力大砖飞地造一个 CSS 引擎

acss 是我们自己的 CSS 样式引擎。它做的事情是：拿到 DOM 和样式表，算出每个元素最终的样式，交给排版和绘制。在它之前，我们的运行时（[libacde](https://github.com/0x00-Community/libacde)，基于 [blitz](https://github.com/DioxusLabs/blitz)）用的是 stylo，也就是 Firefox 和 Servo 的样式引擎，久负盛名，打磨多年。

2026 年 11 月 17 日我们开了 acss 的仓库，到 11 月 24 日：600 多个提交，5 万多行 Rust，blitz 里的 stylo 被整个拿掉，运行时的每一处样式都由 acss 来算。架构参照 stylo，代码一行没抄（stylo 是 MPL，我们的代码要自己的）。代码几乎全是 agent 写的。

我不读引擎的代码。5 万行，一周写出来，人也读不过来。

那凭什么相信它是对的、而且快？这篇讲的就是这件事：**测试先行**。

## 一、这不是 TDD

先说清楚，「测试先行」听起来像 TDD，但不是一回事。

TDD 的节奏是红、绿、重构：写一个会失败的小测试，写刚好让它通过的代码，再整理。测试是写代码的人自己写的，粒度是一个函数、一个行为，它首先是一种**设计工具**：逼你先想清楚接口。

我们的「先行」先在三个地方：

**先在整个项目之前。** acss 的路线一共七个阶段，第 1 阶段叫「裁判先行」，这个阶段一行引擎代码都没有。只做四件事：stylo 版运行时的 WPT 基线、和 Chrome 逐属性比较的工具、性能基线、一页记分板。记分板上有了 stylo 的全部数字，才开始写第一个属性。

**测试不是写代码的人写的。** 主要的裁判都是 agent 改不了的东西：

| 裁判 | 测什么 | 为什么改不了 |
| --- | --- | --- |
| WPT 的 `css/` | 规范行为 | 浏览器厂商写的几万个测试，钉在一个提交上 |
| Chrome | 真实页面对不对 | 钉在一个版本上，同一个页面逐元素逐属性比 `getComputedStyle`，再比截图 |
| stylo | 换引擎前后一致吗 | 影子模式：两个引擎同时算，逐属性比 |
| webref | 属性表全不全 | W3C 的规范数据，758 个属性 |

还有一个例外：增量重算的裁判是 acss 自己，关掉所有捷径、每次整页从头算。它不是外人，第三节会说它管得住什么、管不住什么。

**测试的作用不是设计，是裁决。** TDD 的测试回答「这个函数是不是我想的那样」；我们的裁判回答「这个引擎是不是对的」，而「对」的定义在我们手里之外。

| | TDD | 测试先行（我们的做法） |
| --- | --- | --- |
| 谁写测试 | 写代码的人 | 浏览器厂商、W3C、另一个引擎 |
| 什么时候 | 每个函数之前 | 整个项目之前 |
| 粒度 | 函数、行为 | 整份规范、整个页面、整轮 WPT |
| 测试是 | 设计工具 | 改不了的裁判 |
| 人看什么 | 代码 | 裁判给的数字和截图 |
| 稀缺的是 | 写代码的时间 | 可信的验证 |

最后一行是关键。TDD 诞生的年代，写代码贵，测试是让写代码更稳的辅助。agent 时代反过来了：写代码几乎免费，一晚上几十个提交；但**判断这些代码对不对的成本一点没降**。人审代码的速度跟不上 agent 写代码的速度，所以人干脆不审代码，审裁判。

## 二、力大砖飞

「力大砖飞」是说：不靠巧，靠量。

一个成熟的 CSS 引擎有几百个属性、几十种值类型、选择器、层叠、`@layer`、`@container`、`:has()`、自定义属性、动画、过渡……每一块都有大量边角。过去一个小团队做这件事，得按年算。agent 把「量」的成本打下来了：它不累、不烦、不跳步，失败了就一个一个地看。

但量要有方向。没有裁判，agent 写得越多，错得越多，而且错得越自信。有了裁判，量才变成进度。

举一个具体的例子。

第 1 阶段量基线的时候，我们发现一件怪事：同样是 stylo（servo 模式；两边的版本没有逐一核对），在 Servo 里能过只测样式的那批 WPT 的 73.4%，在我们的 stylo 版运行时里只有 29.3%（只跑了一遍）。差了 44 个百分点。

人看到这里，大概会猜「是不是 stylo 版本不一样」。我们让 agent 把 Servo 过、我们不过的 27340 个子测试**逐条分桶**：

| 原因 | 子测试数 |
| --- | --- |
| `getComputedStyle()` 返回的对象上没有属性名 | 11803 |
| `el.style.x = 非法值` 也收下了 | 6914 |
| `el.style.x` 读回来不是规范化的写法 | 3767 |
| 整个文件出错或超时 | 2014 |
| 选择器和 `insertRule` 的校验 | 1081 |
| **计算值本身不对** | **176** |
| 没归类 | 1585 |

计算值本身算错的只有 176 个。归了类的里头，绝大部分出在 JS 和样式引擎之间的那层：那时候的 CSSOM 是用 JS 另写了一遍的。这个结论直接改了设计：`el.style`、`getComputedStyle`、CSSOM 的读写全部直接落到 acss 上，JS 那层只转发、不解析。

这种活人做不起：两万七千条，一条一条归类。agent 做得起。这就是力大砖飞：**把人做不起的苦活，变成数字**。

## 三、我们主要用的测试方法

### 1. 把 WPT 搬下宿主：几秒钟的裁判

WPT 的真身要在运行时里跑：起一个服务器，开页面，跑 JS。`css/` 整轮 35000 多个文件，一台机器跑 40 分钟。agent 改一行代码就等 40 分钟，力再大也飞不起来。

所以我们把 WPT 的一部分「搬」到了不用宿主的 Rust 测试里。做法是：在 node 的 `vm` 里把每个测试文件的脚本跑一遍，DOM 和 `CSS` 换成什么都答应的空壳，WPT 的辅助函数（`test_valid_value`、`test_computed_value`、`test_interpolation`……）换成只记参数的版本。这样循环、模板字符串、表驱动的调用都录得下来，不用正则去抠字面量（字面量只抠得到三分之一）。

录下来的调用交给 Rust 测试，照辅助函数的 JS 原样重放到 acss 上。开发机上几秒跑完：

| 裁判 | 判了 | 过了 |
| --- | --- | --- |
| 解析（`test_valid_value` 等） | 29111 次调用 | 28883 |
| 计算值（`test_computed_value` 等） | 14591 次调用 | 14450 |
| 插值（过渡、动画、Web Animations） | 54284 条子测试 | 53950 |

它们是 WPT 的移植，不是 WPT 本身：期望值原样从 WPT 读，但最终的判决仍然是运行时里真的 WPT。

### 2. 棘轮：总数涨了也不放行

每一批提交之前跑一个关（`gate.sh`）：格式、clippy、单元测试，然后把上面三个裁判**逐次调用**的结果和上次认可的基线比。

规则只有一条：**有任何一条从过变成不过，就不放行。总数涨了也不行。**

这条规则是专门针对 agent 的。agent 修一个问题，很容易顺手弄坏另一个，然后汇报「通过数又涨了 200」。看总数，这是进步；看逐条，这是一次没被发现的回退。棘轮只认逐条。

### 3. 差分：拿另一个引擎当答案

很多东西没有现成的期望值，那就找一个「肯定对」的东西来比。

- **影子模式**：换引擎之前，blitz 里两个引擎同时跑，stylo 算一遍，acss 算一遍，逐属性比。
- **增量 = 从头算**：增量重算是样式引擎最难的部分。改了一个 class，哪些元素要重算？漏一个，页面就显示旧样式，人肉眼很难发现。我们的裁判是：每次增量重算之后，拿一个**关掉所有捷径**（不用缓存、不用祖先过滤、每个元素试所有规则）的引擎从头算一遍，两边每个元素的每个属性必须一样。

这个裁判后来变成了我们敢做激进优化的底气，第四节再说。但它有一个盲区：参照也是 acss，两条路共用的代码要是错了，两边错得一样，差分比不出来。这类错只能靠单元测试和 WPT 抓。

### 4. 模糊测试，以及测试裁判本身

增量的裁判做成了模糊测试：随机的字节变成一串操作（建、插、删、移元素，改 class、属性、状态、内联样式，插删样式表，改视口，拨动画时钟），最多 200 步，随机时刻重算，每次都和从头算的比。

光有模糊测试还不够，要问：**它真的抓得到错吗？**

所以我们做了**变异检查**：故意把引擎改坏，看裁判几秒内能不能报出来。比如让「改状态」不标脏，3 秒内报出（元素的 `font-size` 一边 19.2px 一边 16px）；让 `:has()` 的锚点不记兄弟方向，种子 1 就报出。抓不到的变异，补单元测试。改了生成输入的代码，这一组变异要重跑，因为输入分布一变，以前抓得到的可能就抓不到了。

同样的怀疑用在每个裁判上：

- **和 Chrome 比之前，先跑一页答案已知的探针**（16 项）。Chrome 不全过，说明工具坏了，直接停。
- **插值裁判有自检**：只比起点和终点，证明期望那一侧和比较函数是通的。不然实际值全失败时，分不清是引擎坏了还是裁判坏了。
- **碰巧相等**：带 `.sub.` 的 WPT 文件里有 `{{host}}` 这种模板，服务器发出去之前会替换。我们录调用时一开始没替换，期望值里留着字面的 `{{host}}`，而 acss 那时不解析网址、原样输出，两边碰巧相等。137 次调用就这样「过了」，比的其实不是网址。
- **少跑就是失败**：每轮记下该有结果的测试，少了的算失败。不然一片机器没起来，结果看起来「零回退」。
- **故意埋一个回退**，看快查模式抓不抓得到。结果抓不到（那个文件不在快查的样本里）。所以快查只能用来改完自查，不能当验收。

### 5. 分片跑整轮 WPT，和一个不是我们的 bug

整轮 WPT 在三台测试机上分片跑，每台 8 个 worker、13 到 17 分钟。主线跑三遍合成一份期望文件，之后每次只跑候选版本和它比；退步的测试原地再跑两遍，每遍都退步才算真退步。

跑着跑着发现：同一个可执行文件、同一台机器，约 2000 个 reftest 在过和不过之间跳，差别几乎都是「一两个像素差 1」。agent 一路追到了渲染器 vello：它用 `atomicAdd` 把线段排进 16×16 的块，块里线段的顺序随 GPU 调度变，再用 f32 按这个顺序累加覆盖率。**浮点加法不满足结合律**，末位跟着变，正好落在取整边界上的像素就差 1。Mac 上 100 次渲染逐字节一样，Linux 的 Intel 显卡上不一样。

改成定点数累加之后，跳的 reftest 从 1310 个降到 66 个。这个补丁**只用在测试机上**，用户拿到的 vello 一直是原样的。这件事本身和 acss 无关，但它说明了一点：裁判有噪声，裁判就不可信；为了让裁判可信，值得追到别人的代码里去。

### 6. 防糊弄

agent 有一个众所周知的毛病：为了让测试通过，改测试。所以有几条硬规矩：

- 期望文件、跳过列表、页面集的每一处改动，在提交正文和汇报里**逐条列出**。
- 「跳过 / 预期失败」的总数**只降不升**，要升先问人。
- 每个「做完了」都附上证据（命令和输出、截图）；没跑的写「未验证」。
- 定期请独立的审查方（另一个模型或另一位开发者）看代码，**只给代码，不给我们的结论**。

## 四、快，是因为敢

下面是 11 月 21 日的一轮基准（单位毫秒，`acss / stylo`，括号里是倍数，小于 1 是 acss 快）。stylo 一侧是 0.22 版、servo 模式，还在 blitz 里的时候量的。页面是冻结下来的公开网站，测试机单线程钉在一个核上，每种操作 101 次，整套跑 3 遍取中位数：

| 操作 | Wikipedia | Stripe | Tailwind |
| --- | --- | --- | --- |
| 清空一个元素的 class | 0.0053 / 0.0213 (0.25) | 0.0321 / 0.357 (0.09) | 0.0445 / 4.34 (0.01) |
| 插入一棵 100 个元素的子树 | 0.121 / 0.133 (0.91) | 0.128 / 0.445 (0.29) | 0.549 / 5.30 (0.10) |
| 整页重算 | 17.6 / 19.1 (0.92) | 21.4 / 36.2 (0.59) | 16.0 / 18.4 (0.87) |
| 500 个元素跑动画，每帧 | 1.08 / 4.77 (0.23) | 1.00 / 8.88 (0.11) | 0.982 / 9.31 (0.11) |
| 全页过渡，每帧 | 14.7 / 112.7 (0.13) | 5.01 / 52.6 (0.10) | 4.31 / 38.3 (0.11) |

插规则这一项这张表里没放：那一轮 acss 量的是另加一张样式表，和 stylo 的 `insertRule` 不是同一个操作。11 月 23 日补量了同一个操作（acss 的 `insert_rule`），插一条命中约 600 个元素的规则，倍数是 Wikipedia 0.50、Stripe 0.24、Tailwind 0.73；那一轮同一操作的 84 行里，没有一行比 stylo 慢。

acss 不是比 stylo 的作者聪明。快有两个原因：

**一是少算。** 同样一个改动，acss 重算的元素更少。插那条命中约 600 个元素的规则，Wikipedia 上 acss 重算了 582 个，stylo 样式变了的有 1282 个；500 个元素跑动画，acss 每帧重算 500 到 562 个，stylo 是 896 到 1340 个。失效算得越准，要做的活越少。

**二是敢。** 增量重算的每一个捷径（命中列表复用、`:has()` 按锚点失效、动画的快路）都是在赌「这里不用重算」。赌错了就是漏更新，人肉眼很难发现。我们敢赌，是因为每个捷径背后都站着那个「关掉所有捷径、从头算」的参照，模糊测试一秒几千串操作地拿它对答案。**差分裁判把激进优化从冒险变成了常规操作。**

### 诚实的部分

这些数字要这样读：

- **这是单线程的比较。** stylo 一侧用的是顺序模式，它的并行能力这里没有量。
- **测法对 acss 有利**：stylo 每次采样前多跑了一遍排版，所以倍数在 0.8 到 1.0 之间的，我们只算「没显出更快」。
- **不是哪里都快。** 小页面第一次算样式，在我们最近的测量里还比 stylo 慢一些；改内联样式大约慢一倍，问题在宿主同步那一层，还没修完。
- **还没毕业。** 替换 stylo 的毕业标准有四条：WPT 通过数不低于 stylo 版；和 Chrome 的截图看不出差别；每帧样式时间和内存不比 stylo 差；模糊测试连续 24 小时不崩、真实桌面跑一周不崩。我们正在一条一条地做。

## 五、agent 时代，人干什么

回头看这一周，我做的事情很少是写代码，主要是三件：

1. **定裁判。** 什么算对，谁说了算。裁判必须是 agent 改不了的。
2. **定规矩。** 棘轮、逐条列出、只降不升、只给代码不给结论。这些规矩防的不是 agent 坏，是 agent 太想让你满意。
3. **看数字。** 不看代码，看记分板，看截图，看倍数。

力大砖飞，前提是飞机上有仪表盘。agent 给了我们几乎无限的力气；测试先行，是给这股力气装上仪表。
