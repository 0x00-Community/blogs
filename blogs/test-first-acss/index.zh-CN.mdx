# 测试先行：用 agent 力大砖飞，从零造一个 CSS 引擎

2026 年 11 月 17 日到 24 日，八天，我们从零写了一个 CSS 样式引擎 acss：600 多个提交，五万多行 Rust。现在我们的运行时（[libacde](https://github.com/0x00-Community/libacde)，基于 [blitz](https://github.com/DioxusLabs/blitz)）里原来的 stylo 已经整个拿掉了，样式全由 acss 来算：解析样式表、匹配选择器、层叠、算出每个元素的计算值，改了 DOM 只重算该重算的部分，再交给排版和绘制。DOM 本身归 blitz 管，排版和绘制也不归 acss。

acss 的架构参照 stylo，也就是 Firefox 和 Servo 用的那个样式引擎，久负盛名、打磨多年。但代码是净室写的，一行没抄：stylo 是 MPL 许可，我们要自己的代码。

这五万多行几乎全是编码 agent 写的。我没有逐行看过引擎的代码，也看不过来：agent 一晚上能交几十个提交，人审代码的速度早就成了瓶颈。

所以这篇想讲的是：**不看代码，凭什么相信它是对的、而且快？** 我们的答案是先把 agent 改不了的「裁判」立起来，人的工作从审代码，变成设计和维护这套裁判。

## 一、写第一行代码之前，先立裁判

我们管这种做法叫「测试先行」。听起来像 TDD，但不是一回事。

TDD 的节奏是红、绿、重构：开发者自己写一个会失败的小测试，写刚好让它通过的代码，再整理。它诞生在写代码很贵的年代，测试首先是一种**设计工具**，回答的是「这个函数是不是我想的那样」。

agent 时代反过来了：写代码几乎不要钱，**判断代码对不对**才贵。

| | TDD | 我们的测试先行 |
| --- | --- | --- |
| 谁写测试 | 写代码的人自己 | 浏览器厂商、W3C、另一个引擎 |
| 什么时候写 | 每个函数之前 | 整个项目写第一行引擎代码之前 |
| 测多大 | 一个函数、一个行为 | 整套规范测试、真实网页、整轮 WPT |
| 测试是什么 | 帮着设计接口的工具 | 和实现无关、agent 改不了的裁判 |
| 人看什么 | 代码 | 裁判给的数字、差异和截图 |

所以 acss 的路线图一共七个阶段，第 1 阶段就叫「裁判先行」。这个阶段一行引擎代码都不写，只做四件事：stylo 版运行时的 WPT 基线、和 Chrome 逐元素逐属性比较的工具、性能基线、一页记分板。

主要的裁判全是外面的东西，agent 想改断言也改不了：

- **WPT 的 `css/`**：各家浏览器厂商一起维护的几万个规范测试，钉在一个固定的提交上。
- **Chrome**：钉住版本，同一个真实页面逐元素比 `getComputedStyle`，再比截图。
- **stylo**：换引擎之前开「影子模式」，两个引擎同时算，逐属性比。
- **W3C 的 webref**：规范里的属性数据，758 个属性，用来核对属性表全不全。

「力大砖飞」说的是不靠巧、靠量。CSS 有几百个属性、几十种值类型，还有选择器、层叠、`@layer`、`@container`、`:has()`、自定义属性、动画、过渡……每一块都有一堆边角。过去小团队做这件事得按年算；agent 不累、不烦、不跳步，把「量」的成本打下来了。但量得有方向：没有裁判，agent 写得越多错得越多，还错得很自信。有了裁判，量才变成进度。

裁判立起来的第一天就派上了用场。量基线的时候我们发现一件怪事：同样是 stylo（servo 模式，两边的版本没有逐一核对），在 Servo 里能过只测样式的那批 WPT 的 73.4%，在我们的 stylo 版运行时里只有 29.3%（只跑了一遍），差了 44 个百分点。

Servo 过、我们不过的子测试有 27340 个，人一条条看根本看不完。我们让 agent 把它们逐条分桶：

| 原因 | 子测试数 |
| --- | --- |
| `getComputedStyle()` 返回的对象上没有属性名 | 11803 |
| `el.style.x = 非法值` 也收下了 | 6914 |
| `el.style.x` 读回来不是规范化的写法 | 3767 |
| 整个文件出错或超时 | 2014 |
| 选择器和 `insertRule` 的校验 | 1081 |
| **计算值本身算错** | **176** |
| 没归类 | 1585 |

计算值本身算错的只有 176 个。归了类的里头，绝大部分出在 JS 和样式引擎之间的那层：那时候的 CSSOM 是用 JS 另写了一遍的。这个结论直接定了 acss 怎么接进宿主：`el.style`、`getComputedStyle` 和所有 CSSOM 的读写都直接落到 acss 上，JS 那层只转发，不解析。

两万七千条一条条归类，人做不起，agent 做得起。这就是力大砖飞：**把人做不起的苦活，变成数字。**

## 二、让反馈变快，也让裁判本身靠得住

裁判有了，接下来是两件事：验证要快到跟得上 agent 改代码的速度；裁判自己也不能出错。

### 1. 把 WPT 搬下宿主，再加一道棘轮

WPT 的真身要在运行时里跑：起服务器、开页面、跑 JS。`css/` 整轮 35000 多个文件，一台机器跑 40 分钟。agent 改一行就等 40 分钟，力气再大也飞不起来。

所以我们把 WPT 的一部分搬到了不用宿主的 Rust 测试里。用正则去抠测试源码里的字面量，只抠得到约三分之一；我们改成在 node 的 `vm` 里把每个测试文件的脚本真跑一遍，DOM 和 `CSS` 换成什么都答应的空壳，`test_valid_value`、`test_computed_value`、`test_interpolation` 这些辅助函数换成只记参数的版本。这样循环、模板字符串、表驱动生成的调用都录得下来。

录下的调用交给 Rust 测试，照辅助函数原来的语义重放到 acss 上，开发机上几秒跑完：

| 裁判 | 判了 | 过了 |
| --- | --- | --- |
| 解析（`test_valid_value` 等） | 29111 次调用 | 28883 |
| 计算值（`test_computed_value` 等） | 14591 次调用 | 14450 |
| 插值（过渡、动画、Web Animations） | 54284 条子测试 | 53950 |

这套只是秒级的本地反馈，最后算数的还是运行时里真跑的 WPT。

每次提交前要过一道关（`gate.sh`）：格式、clippy、单元测试，然后把上面三个裁判**逐条**的结果和上次认可的基线比。规则只有一条：**有任何一条从过变成不过，就不放行，总数涨了也不行。**

这条是专门对着 agent 定的。agent 修一个问题，很容易顺手弄坏另一个，然后汇报「通过数又涨了 200」。看总数是进步，看逐条是一次藏起来的回退。棘轮只认逐条。

### 2. 防糊弄

agent 有个出了名的毛病：为了让检查变绿，去放宽断言、加跳过列表。它不是坏，是太想让你满意。所以有几条硬规矩：

- 期望文件、跳过列表、页面集的每一处改动，在提交正文和汇报里**逐条列出**。
- 「跳过 / 预期失败」的总数**只降不升**，要升先问人。
- 每个「做完了」都附上能复现的证据（命令、输出、截图）；没跑的写「未验证」。
- 定期请独立的审查方（另一个模型或另一位开发者）看代码，**只给代码，不给我们的结论**。

### 3. 裁判也要测

裁判自己的 bug，往往比引擎的 bug 藏得更深。所以每个裁判我们都要怀疑一遍：

- **探针和自检**：和 Chrome 比之前，先跑一页答案已知的探针（16 项），Chrome 不全过说明工具坏了，直接停。插值裁判有一个只比起点和终点的自检，大批失败的时候，用它分清是引擎坏了还是裁判坏了。
- **碰巧相等**：带 `.sub.` 的 WPT 文件里有 `{{host}}` 这种模板，测试服务器发出去之前会替换。我们录调用时一开始漏了这一步，期望值里留着字面的 `{{host}}`；而 acss 那时还不解析网址、原样输出，两边碰巧相等。137 次调用就这样「过了」，其实根本没测网址。
- **少跑就是失败**：每轮记下该有结果的测试，少了的算失败。不然一台机器没起来，结果看起来是「零回退」。
- **故意埋一个回退**：我们拿一个故意改坏的版本去试快查模式，它没抓到，因为那个文件不在快查的样本里。所以快查只能用来改完自查，不能拿来验收。

### 4. 分片跑整轮 WPT，和一个不是我们的 bug

整轮 WPT 在三台测试机上分片跑，每台 8 个 worker，13 到 17 分钟跑完。主线连跑三遍，合成一份期望文件；之后候选版本只跑一遍和它比，退步的测试原地再跑两遍，每遍都退步才算真退步。

跑着跑着发现：同一个可执行文件、同一台机器，约 2000 个 reftest 在过和不过之间来回跳，差别几乎都是「一两个像素差 1」。agent 一路追到了渲染器 vello：它用 `atomicAdd` 把线段排进 16×16 的块，块里线段的顺序跟着 GPU 调度变，再按这个顺序用 f32 累加覆盖率。**浮点加法不满足结合律**，末位跟着变，正好落在取整边界上的像素就差 1。Mac 上连续 100 次渲染逐字节一样，Linux 的 Intel 核显上就会变。

我们给测试机上的 vello 打了一个定点数累加的补丁（用户拿到的版本一直是上游原样），来回跳的 reftest 从 1310 个降到 66 个。

这件事和 acss 本身无关，但道理很重要：**裁判有噪声，裁判就不可信。** 为了让裁判可信，值得追到别人的代码里去。

## 三、增量重算：差分、模糊测试，和敢做的优化

样式引擎里最容易藏 bug 的是增量重算。改了一个元素的 class 或属性，哪些元素要重算？算多了慢，漏一个，页面就留着旧样式，人眼很难看出来。

这一块我们用了一个内部的差分裁判：每次增量重算之后，另起一个**关掉所有捷径**（不用缓存、不用祖先过滤、每个元素试所有规则）的 acss 从头算一遍，两边每个元素的每个属性必须一样。

然后把它接进模糊测试：一串随机字节解码成最多 200 步操作（建、插、删、移元素，改 class、属性、状态、内联样式，增删样式表，改视口，拨动画时钟），随机时刻重算，每次都和从头算的比。

光有模糊测试还不够，还要问：**它真抓得到 bug 吗？** 所以我们定期做变异测试，故意把引擎改坏，看多久能报出来。比如把「改状态时标脏」去掉，3 秒内就报出某个元素的 `font-size` 一边 19.2px、一边 16px；把 `:has()` 锚点的兄弟方向记录弄坏，种子 1 就抓到了。抓不到的变异，补单元测试。改了生成输入的代码，整组变异要重跑，因为输入分布一变，以前抓得到的可能就抓不到了。

这个裁判也有盲区：参照也是 acss，两条路共用的代码要是错了，两边错得一样，差分比不出来。这部分只能靠 WPT 和单元测试。

### 快，是因为敢

有每秒几千串操作的差分模糊测试兜底，我们才敢在增量重算里做激进的优化：命中列表复用、`:has()` 按锚点精确失效、动画快路。每一个都是在赌「这里不用重算」，赌错了就是漏更新。有那个「从头算」的参照天天对答案，冒险就变成了常规操作。

下面是 11 月 21 日的一轮单线程基准。页面是冻结下来的公开网站；测试机钉在一个 CPU 核上；stylo 一侧是 blitz 里集成的 0.22 版（servo 模式，顺序执行）。每种操作 101 次，整套跑 3 遍取中位数。单位毫秒，`acss / stylo`，括号里是倍数，小于 1 是 acss 快：

| 操作 | Wikipedia | Stripe | Tailwind |
| --- | --- | --- | --- |
| 清空一个元素的 class | 0.0053 / 0.0213 (0.25) | 0.0321 / 0.357 (0.09) | 0.0445 / 4.34 (0.01) |
| 插入一棵 100 个元素的子树 | 0.121 / 0.133 (0.91) | 0.128 / 0.445 (0.29) | 0.549 / 5.30 (0.10) |
| 整页重算 | 17.6 / 19.1 (0.92) | 21.4 / 36.2 (0.59) | 16.0 / 18.4 (0.87) |
| 500 个元素跑动画，每帧 | 1.08 / 4.77 (0.23) | 1.00 / 8.88 (0.11) | 0.982 / 9.31 (0.11) |
| 全页过渡，每帧 | 14.7 / 112.7 (0.13) | 5.01 / 52.6 (0.10) | 4.31 / 38.3 (0.11) |

插规则这一项表里没放：那一轮 acss 量的是另加一整张样式表，和 stylo 的 `insertRule` 不是同一个操作。11 月 23 日补量了同一个操作（acss 的 `insert_rule`，插一条命中约 600 个元素的规则），倍数是 Wikipedia 0.50、Stripe 0.24、Tailwind 0.73；那一轮同一操作的 84 行里，没有一行比 stylo 慢。

快主要快在**少算**。插那条命中约 600 个元素的规则，Wikipedia 上 acss 重算了 582 个元素，stylo 样式变了的有 1282 个；500 个元素跑动画，acss 每帧重算 500 到 562 个，stylo 是 896 到 1340 个。失效算得越准，要干的活越少。

### 诚实的部分

这些数字要这样读：

- **只比了单线程。** stylo 一侧是顺序执行，它的并行能力这里没有量。
- **测法对 acss 有利。** stylo 每次采样前多跑了一遍排版，所以倍数在 0.8 到 1.0 之间的，我们只算「没显出更快」。
- **不是哪里都快。** 小页面第一次算样式，在我们最近的测量里还比 stylo 慢一点；改内联样式大约慢一倍，问题在宿主同步那一层，还在修。
- **还没毕业。** 完全替换 stylo 的毕业标准有四条：WPT 通过数不低于 stylo 版；和 Chrome 的截图看不出差别；每帧样式时间和内存不比 stylo 差；模糊测试连续 24 小时不崩、真实桌面跑一周不崩。我们正在一条一条地做。

## 四、很多个 agent 一起干活的规矩

同一时间常常有好几个 agent 会话在一个仓库里干活：一个在修层叠，一个在测试机上跑整轮 WPT，一个在量性能。光有测试，挡不住架构慢慢跑偏。我们靠下面几条规矩。

### 1. 一份写给 agent 的 `AGENTS.md`，加上编译器

仓库根目录有一份 `AGENTS.md`，六十几行，是每个新会话第一个读的文件。只放三类东西：

- **方向**：比如「架构参考 stylo，实现全部自己写」「目标两个：高性能、高稳定性，冲突时先保稳定」。
- **硬规矩**，每条前面一个 ⛔：不拷 stylo 的代码和数据；非测试代码不写 `unsafe`、不 panic；会放大的输入都有上限；不为过测试改裁判；没跑过的不说做完。
- **文件路由**：一张表，写选择器之前读哪篇、写失效之前读哪篇。

能交给机器的规矩，都交给机器。`Cargo.toml` 的 lint 直接拦掉非测试代码里的 `unsafe`、`unwrap`、`expect`、`panic!` 和下标访问；`AGENTS.md` 里再加一条，不许用 `#[allow]` 绕开。人不审代码，就让编译器替人审：agent 写的 `unwrap()` 根本过不了编译，比提示词里写一百遍「不要 panic」都可靠。

lint 管不到的，靠设计：`var()` 的展开、`calc()` 的嵌套、选择器的嵌套、`@import` 的深度、匹配的步数，每一种会放大的输入都有写死的上限，常量集中在一个模块里，超了就照规范当无效处理，不崩、不卡。

### 2. 文档是唯一的事实来源

`docs/` 下面九篇文档，三千多行，才是 acss 真正的设计：架构、宿主接口、数据模型、层叠、增量、稳定性、验证、路线、版本。几条约定：

- **Rust 代码里不写注释，说明都写进 `docs/`。** 散在五万行代码里的注释，没有哪个会话会去通读；文档集中、有路由，新会话进来按图索骥。
- **一个机制只写一处，写成现在时。** 文档只写「现在怎么做」，经过、日期、谁定的都放在提交信息里，文档不会变成流水账。
- **人的决定和 agent 的提议分开写。** 仓库的第二个提交干的就是这件事。agent 很容易把自己的猜测写成定论，下一个会话再把它当真。所以没问过人的方案，文档里会写明「我们的提议，没问过用户」，人拍过板的才算数。

### 3. 路线只有阶段，没有日期

路线图开头就写着：**不估时间**。人的排期经验套不到 agent 的速度上，估了也是错的。每个阶段只写两件事：做什么，怎样算完。「怎样算完」全由裁判说了算，比如阶段 4 是：增量和整页重算的差分模糊测试通过；影子模式下改 DOM 后和 stylo 没有差异；插规则、改 class、插节点的基准不比 stylo 差。

### 4. 一条主线，机器自己排队

几个会话共用一个工作区，每个只提交自己的路径；一个提交一件事；提交正文写为什么改、怎么验证的。

验证按快慢分给机器：开发机跑几秒的裁判；三台测试机跑分片的整轮 WPT 和模糊测试，每个任务先拿锁，哪台空了哪台先跑，一次交好几个任务也不用人排队。

### 5. 人只看一页

所有裁判的数字汇总在一页记分板上：WPT 通过数和 stylo、Chrome 并排，和 Chrome 的截图对比，性能倍数。我看这一页，决定下一步。

发版也是小步快跑：版本号写在 `Cargo.toml`，blitz 用提交号钉住 acss 的某一版。一周发了 18 个版本，每一版在 `docs/releases.md` 里记一行：改了什么、blitz 要不要跟着改。

## 五、写代码变便宜以后，什么还稀缺

这一周最大的感受是：**写代码这件事，已经民主化了。**

五万行的样式引擎，过去要一个有经验的团队做好几年；现在一两个人带着一群 agent，一周多就能替换掉 stylo。不是因为我们特别厉害，是写代码的边际成本塌了。可以预见，接下来「从头写一个」的项目会越来越多：浏览器引擎、JS 引擎、数据库、编译器。

那还有什么是稀缺的？

### WPT 为什么珍贵

回头看，整个项目里最值钱的东西，不是我们写的五万行代码，而是我们**没写**的那几万个测试。

WPT 是 Chrome、Firefox、Safari 这些浏览器厂商和规范作者十几年里一条一条攒下来的。它值钱在四个地方：

1. **它和实现无关。** 测试不是哪个引擎的作者写给自己的，是几家互相竞争的厂商都得过的。agent 改得了自己的代码，改不了它。
2. **它装着没人想得到的边角。** `cubic-bezier()` 的参数要按 64 位浮点读，不然外推到 0.5 处给不出正好的 −0.5；`.sub.` 文件里的模板要先替换；`getComputedStyle` 的对象上要能用 `in` 查到属性名。这些光读规范推不出来，是各家引擎十几年踩过的坑，一个坑一个测试。
3. **它是共识。** 规范的文字有歧义，测试没有。几家浏览器吵完架，结论落成一个测试。照着测试写，就站在了这些共识上。
4. **它有现成的对照。** wpt.fyi 上有各家浏览器在同一个提交上的结果。我们没自己跑过 Chrome 和 Firefox 的 WPT，直接导入，就有了 Chrome 91.4%、Firefox 87.6%、Servo 73.4% 这几根标尺。

换句话说，**WPT 是一份可以执行的规范。** 有了它，「从零写一个 CSS 引擎」就从一个开放问题，变成了一个可以一点一点逼近的封闭问题。而封闭问题，正是 agent 最擅长的。

我们另一个项目 [j8](https://github.com/0x00-Community/j8)（用 Rust 从零写的 JavaScript 引擎）也是同一个套路：裁判是 TC39 的 test262，基线 42,500 条，解释器和 JIT 都要跑，掉一条就失败。

### 护城河在搬家

写代码不再稀缺，护城河在哪？我们的判断是：**从实现搬到了测试。**

- **有好测试集的领域，会被 agent 很快攻下。** CSS 有 WPT，JavaScript 有 test262，SQL 有 sqllogictest。这些地方新实现会越来越多，越来越便宜。
- **没有测试集的领域，agent 只能瞎飞。** 没有裁判，写得再多也只是「看起来能用」。谁先把「对」写成可执行的测试，谁就定义了这个领域。
- **测试集本身会变成产品。** 过去测试是代码的附属品；以后一份好的一致性测试，可能比任何一个实现都值钱，因为有了它，谁（和谁的 agent）都能造出合格的实现。

所以给我们自己的平台接口，我们也在做一份带校验器和一致性测试的标准：先把「对」写下来，再让实现去追。

### 测试先行也有管不到的地方

公平起见，也说说它的边界：

- **测试只管测到的东西。** WPT 再大也有空白，所以我们还要和 Chrome 逐属性比真实页面，还要冻结公开网站，做一组写引擎时没见过的页面。
- **裁判会有噪声、盲区和 bug。** vello 那一个像素、`{{host}}` 的碰巧相等、差分两边错得一样，都是例子。花在让裁判稳定、可信上的力气，一点不比写引擎少。

## 六、agent 时代，人干什么

回头看这八天，我几乎没写代码，主要干了四件事：

1. **定裁判。** 什么算对，谁说了算。裁判必须是 agent 改不了的。
2. **定规矩。** 棘轮、逐条列出、只降不升、只给代码不给结论。这些规矩防的不是 agent 坏，是 agent 太想让你满意。
3. **拍板。** agent 会给方案，还会给很多方案。走哪条路、哪个功能不做、两个目标冲突时保哪个，这些是人的事。
4. **看数字。** 不看代码，看记分板，看截图，看倍数。

TDD 教会了一代程序员「先写测试」。到了 agent 时代，这句话要升一级：**先定裁判。** 测试不再是写代码的辅助，写代码反而成了通过裁判的手段。

力大砖飞，前提是飞机上有仪表盘。agent 给了我们几乎无限的力气；测试先行，是给这股力气装上仪表。
